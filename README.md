# ACME Talent ETL

A medallion data pipeline (landing -> bronze -> silver -> gold) for HR data: 7 PostgreSQL tables plus a learning-platform event feed. All data is synthetic and generated by the repo. It validates and quarantines bad records, answers 7 talent questions in Gold tables, and publishes a static dashboard and an analysis notebook. It runs in Docker (Postgres + MinIO) locally and in GitHub Actions.

> More detail: [docs/design-spec.md](docs/design-spec.md) (design) and [docs/notes.md](docs/notes.md) (implementation notes).

## Quick start

Needs Docker. The first run generates the synthetic data and creates a git-ignored `.env` with random local passwords.

```powershell
# Windows PowerShell
.\scripts\run_compose.ps1          # all layers + site\
start site\index.html
```

```bash
# Linux / macOS / Git Bash
scripts/run_compose.sh
```

Postgres is exposed on host port 5544. To use another port, set `PG_HOST_PORT` in `.env` or in your shell.

## Generated data

`scripts/generate_data.py` creates the dataset in `data/generated/`, which is not committed. The same `--seed` and `--employees` always give identical files.

```bash
python scripts/generate_data.py --seed 42 --employees 2000
```

It plants data-quality problems on purpose: malformed JSON, duplicate event ids, null employee ids, bad dates (`yesterday`, `N/A`, empty, `2026-13-45`), schema drift (`notes` instead of `text`), and reviews and assessments dated before the hire date. `data/generated/manifest.json` records how many of each, plus the results the pipeline should produce, and the tests check the pipeline against it.

After regenerating with a different seed or size, reset the Docker volumes so Postgres reloads: `.\scripts\run_compose.ps1 -Reset` or `RESET=1 scripts/run_compose.sh`.

## Running one layer

The pipeline is three layers that can run separately. Each one checks that its upstream layer finished (a `_SUCCESS` marker in the lake) and fails fast with a clear message if not.

| Layer | Does | Needs first |
| --- | --- | --- |
| `bronze` | extract Postgres + JSONL to `landing/`, copy to `bronze/` (1 check) | Postgres with the generated data |
| `silver` | validate, quarantine, write `silver/` | a completed bronze run |
| `gold` | 7 Gold tables, 8 checks, site data; then builds `site/` | a completed silver run |
| `all` | all three, in order | |

```powershell
# Windows PowerShell
.\scripts\run_layer.ps1 -Layer bronze
.\scripts\run_layer.ps1 -Layer silver
.\scripts\run_layer.ps1 -Layer gold            # also builds site\ (add -SkipSite to skip)
```

```bash
# Linux / macOS / Git Bash
scripts/run_layer.sh bronze
scripts/run_layer.sh silver
scripts/run_layer.sh gold
```

Without the scripts (inside the image, or with a local Python):

```bash
python job.py --layer silver        # or LAYER=silver; STEPS=... still works
```

How to tell what state the pipeline is in:
- `lineage/latest.json` in the lake (and `site/lineage.json`) shows the overall status: `SUCCEEDED`, `INCOMPLETE` (a layer hasn't run yet), `STALE` (a layer was built from different upstream data; rerun it) or `FAILED`, and each layer's latest run.
- Each layer's own history is in `lineage/<layer>/runs/`. Silver records the bronze run it read, and gold records the silver (and bronze) run.
- Staleness compares data checksums, so re-running a layer on unchanged input is safe. If bronze really changed, gold warns until you rerun silver.

### In GitHub Actions

`.github/workflows/pipeline.yml` runs `bronze -> silver -> gold` as three jobs on every push to `main`. To run one layer alone: **Actions > pipeline > Run workflow** and pick `layer`. Jobs hand the lake to each other as artifacts (`lake-after-<layer>`, kept 7 days); a single-layer run starts from the newest saved state. The dashboard is published to **GitHub Pages** by the `deploy` job, only from `main`, only when all three layer jobs succeeded in the same run, and only when the pipeline ended SUCCEEDED with 9/9 checks. One-time setup: **Settings > Pages > Source = GitHub Actions**. See [docs/notes.md](docs/notes.md#ci-how-the-lake-moves-between-jobs) for why the state moves this way.

## Tests

```bash
scripts/run_tests.sh               # unit + integration (starts Postgres + MinIO), with coverage
UNIT_ONLY=1 scripts/run_tests.sh   # no Docker
```

Do the [Python setup](#python-setup) first. On Windows, run it with Git Bash: `& "C:\Program Files\Git\bin\bash.exe" scripts/run_tests.sh`.
